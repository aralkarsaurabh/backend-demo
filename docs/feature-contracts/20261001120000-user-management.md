# Feature Contract: User Management

> **Status:** AGREED v1, implemented 2026-10-01. Builds on `20261001073651-authentication-authorization.md` (FC-AUTH-001) and `20261001103000-organizations.md` (FC-ORG-001); nothing in either changes.

## Decisions for v1

| # | Decision | Consequence |
|---|---|---|
| **D11** | **`User.status` (`ACTIVE`/`SUSPENDED`/`DEACTIVATED`) is a platform property, like `User.role`.** It affects authentication only, never organization membership. | A suspended user keeps their memberships; they just cannot sign in. Organization roles are untouched. |
| **D12** | **Suspending or deactivating revokes all of the user's refresh tokens; D1 is kept.** `authenticate()` still does no database read. | An access token issued before the change keeps working until it expires (≤15 min). The user cannot obtain a new one. Immediate cut-off would mean a status read per request and is deliberately not done. |
| **D13** | **A status block is revealed only after the password is verified.** Login returns `ACCOUNT_SUSPENDED` / `ACCOUNT_DEACTIVATED` only for a correct password; otherwise `INVALID_CREDENTIALS`. | The unknown-email / wrong-password sameness (FC-AUTH-001) is preserved. |
| **D14** | **An admin cannot change their own status** (`CANNOT_CHANGE_OWN_STATUS`). | The last admin cannot lock themselves out. |
| **D15** | **Account update is `name` only.** Email changes need email verification and are out of scope. | Unknown fields (`role`, `status`, `email`) are rejected with `VALIDATION_ERROR`, not ignored. |

## 2. Business Objective

Let users see and maintain their own account (profile, name, password) and let platform admins disable accounts, without changing authentication or organization behaviour.

## 3. User Story

As a signed-in user, I want to view my profile, rename myself and change my password, so that my account stays accurate and secure. As a platform admin, I want to suspend or deactivate an account, so that it can no longer sign in.

## 4. Actors

- Authenticated user (`USER` or `ADMIN`): profile, update name, change password, for themselves only.
- Platform `ADMIN`: change another user's status.
- Organization `OWNER`/`ADMIN`: **no** power over platform status.

## 5. Entry Point

API only: `/api/v1/users/me`, `/api/v1/users/me/password`, `/api/v1/users/:userId/status`.

## 6. UI Reference

N/A. No frontend in this repository.

## 7. User Flow

1. Profile: `GET /users/me` returns the account from the database.
2. Rename: `PATCH /users/me` with `name`.
3. Change password: `POST /users/me/password` with the current and new password. On success every refresh token of the user is revoked, so the client must sign in again.
4. Suspend/deactivate: an admin calls `PATCH /users/:userId/status`. The target's refresh tokens are revoked; their login and refresh are denied until reactivated.

## 8. Fields

| Field | Type | Required | Endpoint | Validation |
|---|---|---|---|---|
| `name` | string | yes | PATCH /users/me | trimmed, 1-100 chars |
| `currentPassword` | string | yes | POST /users/me/password | 1-72 chars, not trimmed |
| `newPassword` | string | yes | POST /users/me/password | 8-72 chars, not trimmed, same policy as registration |
| `status` | enum | yes | PATCH /users/:userId/status | `ACTIVE`, `SUSPENDED`, `DEACTIVATED` |
| `userId` | uuid | yes | path | valid UUID |

## 9. Validation Rules

Bodies are strict: any field not listed above is a `VALIDATION_ERROR`. No complexity rules are added to passwords.

## 10. Business Rules

- New users are `ACTIVE`; existing users are `ACTIVE` after the migration.
- Allowed transitions: `ACTIVE`→`SUSPENDED`/`DEACTIVATED`; `SUSPENDED`→`ACTIVE`/`DEACTIVATED`; `DEACTIVATED`→`ACTIVE`.
- Repeating `SUSPENDED` or `DEACTIVATED` gives `USER_ALREADY_SUSPENDED` / `USER_ALREADY_DEACTIVATED`. Any other disallowed transition (including `ACTIVE`→`ACTIVE`) gives `INVALID_USER_STATUS`.
- Moving to `SUSPENDED` or `DEACTIVATED` revokes all refresh tokens of the target. Moving to `ACTIVE` revokes nothing.
- Login and refresh reject non-`ACTIVE` accounts. Refresh reads the status from the database.
- `SUSPENDED` and `DEACTIVATED` behave identically; the difference is business meaning only.
- Changing the password does not require the new one to differ from the current one.

## 11. API Contracts

All responses use the standard envelope.

| Method | Path | Auth | Request | Success |
|---|---|---|---|---|
| GET | `/users/me` | access token | none | 200 `{ user: { id, name, email, role, status, createdAt, updatedAt } }` |
| PATCH | `/users/me` | access token | `{ name }` | 200 `Account updated successfully.`, same `user` shape |
| POST | `/users/me/password` | access token | `{ currentPassword, newPassword }` | 200 `data: null` |
| PATCH | `/users/:userId/status` | access token, `ADMIN` | `{ status }` | 200 `User status updated successfully.`, same `user` shape |

Login and refresh gain `403 ACCOUNT_SUSPENDED` / `403 ACCOUNT_DEACTIVATED`.

## 12. Backend Processing Flow

- **Change password:** authenticate → validate → load user → compare current password → hash new → update hash → revoke all refresh tokens → 200.
- **Update status:** authenticate → authorize(ADMIN) → validate → reject self → load target → check transition → update status → if not `ACTIVE`, revoke all refresh tokens → 200.
- **Login:** find user → compare password → check status → issue tokens.

## 13. Database Impact

New enum `UserStatus` and column `User.status` (default `ACTIVE`), migration `20261001120000_add_user_status`. No new tables or indexes. `revokeAllForUser` is one `UPDATE ... WHERE userId = ? AND revokedAt IS NULL`.

## 14. Permissions

| Action | USER | ADMIN | Org OWNER/ADMIN |
|---|---|---|---|
| View / rename self, change own password | ✅ | ✅ | ✅ (as a user) |
| Change another user's status | ❌ | ✅ | ❌ |
| Change own status | ❌ | ❌ | ❌ |

## 15. Error Codes

New: `INVALID_CURRENT_PASSWORD` 400, `ACCOUNT_SUSPENDED` 403, `ACCOUNT_DEACTIVATED` 403, `USER_ALREADY_SUSPENDED` 409, `USER_ALREADY_DEACTIVATED` 409, `INVALID_USER_STATUS` 409, `CANNOT_CHANGE_OWN_STATUS` 403. Reused: `VALIDATION_ERROR`, `USER_NOT_FOUND`, `UNAUTHORIZED`, `FORBIDDEN`. `INVALID_CURRENT_PASSWORD` is 400, not 401, so clients do not treat it as an expired session.

## 16. Frontend Behaviour

N/A. Clients branch on `error.code`. After a password change, discard stored tokens and sign in again.
