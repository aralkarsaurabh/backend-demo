## 2. Business Objective

Let the members of an organization record follow-up work, say who owns it and when it is due, and track it to completion.

## 3. User Story

As a member of an organization, I want to create tasks, assign them to colleagues, give them a due date and move them through a status, so that nothing I owe a lead or customer is forgotten.

## 4. Actors

- `OWNER`, `ADMIN` and `MEMBER` of the organization: read, create, update and assign tasks.
- `OWNER` and `ADMIN` only: delete tasks.
- A non-member, and a platform `ADMIN` who is not a member, have no access (`404 ORGANIZATION_NOT_FOUND`, D5, D9, D10).

## 5. Entry Point

HTTP API only, under `/api/v1/organizations/:organizationId/tasks`.

## 6. UI Reference

N/A: no UI in this repository. The API reference is `documentation/tasks.md`.

## 7. User Flow

1. A member creates a task with a title (and optionally a description, an assignee and a due date). It starts as `TODO`.
2. The member or a colleague updates it: changes the text, the assignee or the due date, or moves the status `TODO` → `IN_PROGRESS` → `COMPLETED`.
3. Anyone can list the organization's tasks, filtered by status, assignee, due-date range, overdue, or a search text.
4. A completed or cancelled task stays queryable and can be reopened by setting another status.
5. An `OWNER` or `ADMIN` deletes a task that is no longer wanted.

## 8. Fields

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | uuid | server | |
| `organizationId` | uuid | server | never in a body or a response |
| `title` | string | yes on create | 1-200 characters after trimming |
| `description` | string | no | 1-2000 characters; `null` clears on update |

| `dueDate` | ISO 8601 timestamp with offset | no | stored as UTC; `null` clears on update |
| `status` | enum | server on create (`TODO`); optional on update | `TODO`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED` |
| `createdAt`, `updatedAt` | timestamp | server | |

## 9. Validation Rules

- Create and update bodies are strict objects: `organizationId`, `id`, `createdAt`, `updatedAt` and any other unknown key are `400 VALIDATION_ERROR`. `status` is rejected on create.
- Update needs at least one field.
- `title` cannot be cleared; `description`, `assignedToUserId` and `dueDate` can be set to `null`.
- Path ids must be uuids. List query is strict: `page` >= 1 (default 1), `limit` 1-100 (default 20), `sortBy` in `createdAt | dueDate | title` (default `createdAt`), `sortOrder` `asc | desc` (default `desc`), `status` an enum value, `assignedToUserId` a uuid, `dueFrom` / `dueTo` dates like `2026-10-01` (inclusive, UTC; `dueFrom` after `dueTo` is invalid), `overdue` only `true`, `search` 1-100 characters.

## 10. Business Rules

- **D45:** a task belongs to one organization. Every `TaskRepository` method takes `organizationId` and filters on it. Access comes from the organization membership, never `User.role`. A task of another organization is `404 TASK_NOT_FOUND`.
- **D46:** the assignee must be a current member of the same organization (`400 ASSIGNED_USER_NOT_MEMBER`, the same error for an unknown user), checked by `AssignTask` on create and on update. Unassigned is valid.
- **D47:** status is a plain label with no transition guard: any status may be set from any other, so a `COMPLETED` or `CANCELLED` task can be reopened. `COMPLETED` is not deleted. No `TASK_ALREADY_COMPLETED` or `INVALID_TASK_STATUS` code exists; an unknown status is `VALIDATION_ERROR`.
- **D48:** overdue is derived, never stored: `status NOT IN (COMPLETED, CANCELLED) AND dueDate < now()`, applied as a query condition for `overdue=true`.
- **D49:** hard delete, no soft delete or audit history.
- **D50:** sorting is a whitelist, the order always ends in `id`, `dueDate` sorts nulls last, and search escapes `%` and `_`.
- **D51:** a task has no link to a lead or customer in this version.
- Assigning or unassigning (`assignedToUserId` present in a body, including `null`) needs `task:assign` as well as the route's `task:create` / `task:update`.

## 11. API Contracts

Base path `/api/v1/organizations/:organizationId/tasks`. All routes need `Authorization: Bearer <access token>`. All responses use the standard envelope. A task is `{ id, title, description, assignedToUserId, dueDate, status, createdAt, updatedAt }` (timestamps ISO strings, `null` for empty optionals); a list item leaves out `description`.

| Method | Path | Permission | Success |
|---|---|---|---|
| `POST` | `/` | `task:create` (+ `task:assign` if `assignedToUserId` sent) | `201` `{ task }` |
| `GET` | `/` | `task:read` | `200` `{ tasks, pagination }` |
| `GET` | `/:taskId` | `task:read` | `200` `{ task }` |
| `PATCH` | `/:taskId` | `task:update` (+ `task:assign` if `assignedToUserId` present) | `200` `{ task }` |
| `DELETE` | `/:taskId` | `task:delete` | `200` `data: null` |

Create body: `{ "title": "Follow up with Rahul", "description": "Discuss enterprise pricing", "assignedToUserId": "<uuid>", "dueDate": "2026-10-05T12:00:00.000Z" }`. Update body: any of `title`, `description`, `assignedToUserId`, `dueDate`, `status`.

`pagination` is `{ page, limit, totalItems, totalPages, hasNextPage, hasPreviousPage }`, as for customers and leads. Failures: see section 15.

## 12. Backend Processing Flow

Route → `authenticate` → `requireOrganizationMembership` → `requireOrganizationPermission` → `TaskController` (Zod validation, body-dependent `task:assign` check) → use case → `TaskRepository` → `PrismaTaskRepository`. `UpdateTask`: find the task (404), run `AssignTask` when the body assigns a user, then a guarded `update`; a task deleted in between is `404`.

## 13. Database Impact

New enum `TaskStatus` and table `Task` (`id`, `organizationId`, `title`, `description?`, `assignedToUserId?`, `dueDate?`, `status` default `TODO`, `createdAt`, `updatedAt`). Foreign keys: `organizationId` → `Organization` `ON DELETE CASCADE`; `assignedToUserId` → `User` `ON DELETE SET NULL`. Indexes: `(organizationId, createdAt)`, `(organizationId, status)`, `(organizationId, assignedToUserId)`, `(organizationId, dueDate)`. No transaction beyond single statements (the list runs count and page in one `$transaction`). Migration `20261001210500_add_tasks`.

## 15. Error Codes

| Code | Status | When |
|---|---|---|
| `TASK_NOT_FOUND` | 404 | unknown task id, or a task of another organization |
| `ASSIGNED_USER_NOT_MEMBER` | 400 | assignee is not a member (existing code) |
| `VALIDATION_ERROR` | 400 | any invalid body, query or path (existing code) |
| `INSUFFICIENT_ORGANIZATION_PERMISSION` | 403 | the role lacks the permission (existing code) |
| `ORGANIZATION_NOT_FOUND` | 404 | non-member or unknown organization (existing code) |

## 20. Test Cases

- Unit: request schemas (strict, trimming, nullable clears, dates, query defaults and bounds), use cases (organization isolation, assignment rule, any-to-any status, derived overdue and filters, sorting, pagination), permission matrix.
- Real SQL (`tests/integration/task-repositories.test.ts`): organization scoping of every method, cascade on organization delete, `SET NULL` on user delete, escaped search, overdue condition (excludes `COMPLETED`, `CANCELLED` and no-due-date tasks), total sort order with `dueDate` nulls last, due-range bounds; each guard proven to fail when removed.
- HTTP (`tests/integration/tasks.http.test.ts`): every route per role, envelope, strict bodies, cross-organization `404`, `task:assign` on `PATCH`, delete denied for `MEMBER`.

## 21. Dependencies

Organizations (membership, permissions) and the shared envelope, validation and pagination helpers. Independent of customers, leads and pipelines.

## 23. Future Improvements

Out of scope now: linking a task to a lead or customer, a dedicated `/assign` endpoint, status history, a transition guard (for example a terminal `CANCELLED`), recurring tasks, reminders and notifications, comments, soft delete, trigram or full-text search, and reassigning or unassigning tasks when a member is removed from the organization (a removed member stays assigned, as for leads).
