## 2. Business Objective

Let an organization model its sales process as ordered stages and move leads through them, without redefining the business meaning of `Lead.status`.

## 3. User Story

As an organization member, I want to see my leads laid out across the stages of a sales pipeline and move a lead from stage to stage, so that my team can see where each deal stands. As an organization admin, I want to define the pipelines and their stages and order them, so that the process matches how we sell.

## 4. Actors

- Organization `OWNER` and `ADMIN`: manage pipelines and stages, move leads, read.
- Organization `MEMBER`: read pipelines and the summary, move leads.
- Platform `User.role` is never consulted (D10, D16).
- Non-members get `404 ORGANIZATION_NOT_FOUND` (D9).

## 5. Entry Point

API only. There is no UI in this repository. A future UI would show a pipeline board backed by `GET .../pipelines/:pipelineId/summary` and `PATCH .../leads/:leadId/stage`.

## 7. User Flow

1. An admin creates a pipeline (`POST .../pipelines`).
2. The admin adds stages one by one; the server appends each at the next position.
3. The admin may rename a stage, reorder all stages with one call, or delete a stage that holds no leads.
4. A member moves a lead into a stage (`PATCH .../leads/:leadId/stage`). Moving into another stage of the same or another pipeline of the same organization is allowed.
5. Anyone in the organization reads the summary: leads per stage and the total.
6. To remove a pipeline, an admin first empties each stage of leads, deletes the stages, then deletes the pipeline.

Failure paths: unknown or foreign pipeline/stage is `404`; duplicate name is `409`; a stage that still holds leads cannot be deleted (`409`); a pipeline that still has stages cannot be deleted (`409`); a converted lead cannot be moved (`409`); a reorder list that is not an exact permutation of the pipeline's stages is `400`.

## 9. Validation Rules

- All request bodies use strict Zod schemas: unknown keys, including `organizationId`, `pipelineId` and `position`, are `400 VALIDATION_ERROR`.
- Names are trimmed before validation and before the uniqueness check; whitespace-only names are rejected.
- Update bodies require at least one field.
- `stageIds` (reorder) is a non-empty array of uuid strings, at most 100 entries.
- `pipelineStageId` (move) is a uuid.
- Path ids that are not uuids are `400 VALIDATION_ERROR`.

## 10. Business Rules

- **D34:** A pipeline belongs to one organization; a stage belongs to one pipeline; a lead references at most one stage. Ownership chain: Lead → PipelineStage → Pipeline → Organization. Every repository method takes the organization id (and the pipeline id for stages) and filters on it. A stage is resolved through its pipeline's `organizationId`, so a stage of another organization is `404 PIPELINE_STAGE_NOT_FOUND`.
- **D35:** `PipelineStage` is not `Lead.status`. `status` stays the business state (`NEW` .. `CONVERTED`); a stage is a position in one process. Neither constrains the other. `PATCH /leads/:leadId` does not accept `pipelineStageId`, and a stage move never changes `status`.
- **D36:** `Lead.pipelineStageId` is nullable so existing leads stay valid. Creating a lead does not assign a stage.
- **D37:** Positions are server-assigned, 0-based and contiguous. Creating a stage appends at `max + 1` (or 0). Deleting a stage compacts the positions after it in the same transaction. Clients can only reorder, never set a position.
- **D38:** Reorder is one repository method and one transaction. The pipeline row is locked (`SELECT ... FOR UPDATE`) so concurrent reorders and stage creations serialise. The submitted `stageIds` must be an exact permutation of the pipeline's current stage ids (no duplicate, none missing, none foreign), otherwise `400 INVALID_STAGE_ORDER` and nothing changes. Because `(pipelineId, position)` is unique, positions are rewritten in two phases (offset out of range, then final values) inside the transaction.
- **D39:** Stage creation takes the same pipeline row lock before reading the next position; the unique constraint is the backstop.
- **D40:** Names are unique per scope after trimming, case-sensitive: `(organizationId, name)` for pipelines and `(pipelineId, name)` for stages. A violation is `409 PIPELINE_ALREADY_EXISTS` / `409 PIPELINE_STAGE_ALREADY_EXISTS`. The database constraint is the guard; the use case does not pre-check alone.
- **D41:** A stage that holds leads cannot be deleted (`409 PIPELINE_STAGE_IN_USE`). A pipeline that still has stages cannot be deleted (`409 PIPELINE_NOT_EMPTY`). Leads are never silently deleted or orphaned. The database foreign key from `Lead.pipelineStageId` (`ON DELETE NO ACTION`) is the mechanism: deleting a stage that holds a lead, including one moved in concurrently, is refused by the database and the violation maps to `PIPELINE_STAGE_IN_USE`.
- **D42:** Moving a lead is `MoveLeadToStage`: the lead must exist in the organization (`LEAD_NOT_FOUND`), the stage must belong to a pipeline of the same organization (`PIPELINE_STAGE_NOT_FOUND`), and the lead must not be converted (`409 LEAD_ALREADY_CONVERTED`). The write is a guarded update (`WHERE id AND organizationId AND status <> 'CONVERTED'`) so a concurrent conversion cannot be overwritten (same guard as D31). Moving to the stage the lead is already in succeeds and changes nothing material.
- **D43:** The summary is a database aggregation (`LEFT JOIN` + `GROUP BY` on the stage), so empty stages appear with `leadCount: 0`. Leads are never loaded into Node. `totalLeads` is the sum of the stage counts; leads with no stage and leads of other pipelines are not counted.
- **D44:** Hard delete for pipelines and stages. No soft delete.
- Permissions come from the organization membership (D5, D16). The JWT carries no organization data.

## 11. API Contracts

All endpoints require `Authorization: Bearer <accessToken>` and use the standard envelope `{ success, message, data, error, meta: { timestamp } }`. Base path `/organizations/:organizationId`. Middleware chain: `authenticate` → `requireOrganizationMembership` → `requireOrganizationPermission(<permission>)` → controller (Zod) → use case → repository.

| Method | Path | Permission | Success |
|---|---|---|---|
| POST | `/pipelines` | `pipeline:create` | 201 `{ pipeline }` |
| GET | `/pipelines` | `pipeline:read` | 200 `{ pipelines }` (each with `stages`) |
| GET | `/pipelines/:pipelineId` | `pipeline:read` | 200 `{ pipeline }` with stages ordered by position |
| PATCH | `/pipelines/:pipelineId` | `pipeline:update` | 200 `{ pipeline }` |
| DELETE | `/pipelines/:pipelineId` | `pipeline:delete` | 200, `data: null` |
| POST | `/pipelines/:pipelineId/stages` | `pipeline:manage_stages` | 201 `{ stage }` |
| PATCH | `/pipelines/:pipelineId/stages/reorder` | `pipeline:manage_stages` | 200 `{ pipeline }` with stages in the new order |
| PATCH | `/pipelines/:pipelineId/stages/:stageId` | `pipeline:manage_stages` | 200 `{ stage }` |
| DELETE | `/pipelines/:pipelineId/stages/:stageId` | `pipeline:manage_stages` | 200, `data: null` |
| PATCH | `/leads/:leadId/stage` | `pipeline:move_lead` | 200 `{ lead }` |
| GET | `/pipelines/:pipelineId/summary` | `pipeline:read` | 200 summary |

The `reorder` route is registered before `/stages/:stageId`.

### Request bodies

- Create pipeline: `{ "name": "Sales Pipeline", "description": "Standard B2B sales process" }` (`description` optional).
- Update pipeline: `{ "name"?: string, "description"?: string | null }`, at least one key.
- Create stage: `{ "name": "Demo Scheduled" }`.
- Update stage: `{ "name": string }`. Position is not updatable here.
- Reorder: `{ "stageIds": ["stage-3", "stage-1", "stage-2", "stage-4"] }`.
- Move lead: `{ "pipelineStageId": "<uuid>" }`.

### Success shapes

```json
{ "pipeline": { "id": "...", "name": "Sales Pipeline", "description": "...", "stages": [], "createdAt": "...", "updatedAt": "..." } }
```

```json
{ "stage": { "id": "...", "pipelineId": "...", "name": "Contacted", "position": 1, "createdAt": "...", "updatedAt": "..." } }
```

Summary:

```json
{
  "pipeline": { "id": "...", "name": "Sales Pipeline" },
  "stages": [{ "id": "...", "name": "New Lead", "position": 0, "leadCount": 32 }],
  "totalLeads": 67
}
```

The lead representation (all lead endpoints) gains `pipelineStageId: string | null`.

## 12. Backend Processing Flow

**Create stage:** authenticate → membership → permission → Zod → `CreatePipelineStage` → verify the pipeline exists in the organization (`PIPELINE_NOT_FOUND`) → repository `create` (transaction: lock pipeline row, read next position, insert; unique violation on name → `PIPELINE_STAGE_ALREADY_EXISTS`) → respond.

**Reorder:** … → `ReorderPipelineStages` → repository `reorder` (transaction: lock pipeline row, load stage ids, compare as a set with the request and reject duplicates, missing and foreign ids, two-phase position rewrite) → reload pipeline → respond.

**Delete stage:** … → `DeletePipelineStage` → repository `delete` (transaction: lock pipeline row, delete the stage, compact the later positions in two phases; stage missing → `PIPELINE_STAGE_NOT_FOUND`, FK violation because a lead is in the stage → `PIPELINE_STAGE_IN_USE`).

**Delete pipeline:** … → `DeletePipeline` → repository `delete` (refuses when stages exist → `PIPELINE_NOT_EMPTY`; the check and delete are atomic).

**Move lead:** … → `MoveLeadToStage` → `PipelineStageRepository.findById(organizationId, stageId)` → `LeadRepository.moveToStage(organizationId, leadId, stageId)` (guarded update; no match is disambiguated into `LEAD_NOT_FOUND` or `LEAD_ALREADY_CONVERTED` by a follow-up read) → respond.

**Summary:** … → `GetPipelineSummary` → verify pipeline → repository aggregation query → respond.

## 13. Database Impact

New migration `prisma/migrations/<timestamp>_add_pipelines/migration.sql`, generated with `prisma migrate diff`, reviewed, applied with `migrate deploy`. No existing migration is edited.

- Table `Pipeline`: `organizationId` FK → `Organization` `ON DELETE CASCADE`; unique `(organizationId, name)`; index covered by that unique.
- Table `PipelineStage`: `pipelineId` FK → `Pipeline` `ON DELETE CASCADE`; unique `(pipelineId, position)`; unique `(pipelineId, name)`.
- Table `Lead`: new nullable `pipelineStageId` FK → `PipelineStage` `ON DELETE NO ACTION`; index `(pipelineStageId)` for the summary and the foreign key checks. `NO ACTION` rather than `RESTRICT` because it is checked at the end of the statement: a stage with a lead still cannot be deleted by itself, but deleting an organization can cascade to its stages and leads in one statement (`RESTRICT` would fail that).
- Transaction boundaries: `PipelineStageRepository.create`, `reorder`, `delete`, and `PipelineRepository.delete`. Existing leads need no backfill.
- Cascade note: deleting an organization cascades to pipelines and stages and to leads; deletion order inside that cascade is handled by Postgres. This is the one path that bypasses `PIPELINE_STAGE_IN_USE`, because the leads go with the organization.

## 15. Error Codes

Each new code is added to `ErrorCode`, `ERROR_HTTP_STATUS`, `ERROR_DEFAULT_MESSAGE`, the documentation and this contract.

| Code | HTTP | When |
|---|---|---|
| PIPELINE_NOT_FOUND | 404 | No such pipeline in this organization (including another organization's) |
| PIPELINE_STAGE_NOT_FOUND | 404 | No such stage in this pipeline / organization |
| PIPELINE_ALREADY_EXISTS | 409 | A pipeline with this name exists in the organization |
| PIPELINE_STAGE_ALREADY_EXISTS | 409 | A stage with this name exists in the pipeline |
| PIPELINE_NOT_EMPTY | 409 | Deleting a pipeline that still has stages |
| PIPELINE_STAGE_IN_USE | 409 | Deleting a stage that still holds leads |
| INVALID_STAGE_ORDER | 400 | `stageIds` is not an exact permutation of the pipeline's stages |

Reused: `VALIDATION_ERROR`, `LEAD_NOT_FOUND`, `LEAD_ALREADY_CONVERTED`, `INSUFFICIENT_ORGANIZATION_PERMISSION`, `ORGANIZATION_NOT_FOUND`, `UNAUTHORIZED`, `INTERNAL_SERVER_ERROR`.

Not added on purpose: a separate "stage not in pipeline" code (a stage of another pipeline or organization is indistinguishable from a missing one, `PIPELINE_STAGE_NOT_FOUND`).

## 20. Test Cases

**Unit (fakes):** each use case; cross-organization stage rejected; reorder rejects duplicate, missing and foreign ids; move rejects a converted lead; delete rules; permission matrix for the six new permissions on all three roles; Zod schemas (strict, trimming, bounds, `position` rejected).

**HTTP integration:** each endpoint's happy path and envelope; `401` without a token; `404` for non-members and for another organization's pipeline, stage and lead; `403` for `MEMBER` on create/update/delete/manage_stages and `200` on read and move; duplicate names `409`; reorder result order; `PATCH /leads/:id` with `pipelineStageId` is `400`; lead responses include `pipelineStageId`; summary counts including an empty stage and `totalLeads`.

**Real-SQL repository tests** (`tests/integration/pipeline-repositories.test.ts`), each proving the guard fails when removed:
- Every method filters on the organization (and pipeline).
- `(pipelineId, position)` and both name unique constraints reject duplicates.
- Reorder rewrites atomically: a failing reorder leaves the original order; the two-phase rewrite does not hit the unique constraint.
- Concurrent stage creation yields distinct contiguous positions.
- Stage delete compacts positions and is blocked while a lead is in the stage, including a concurrent move.
- Pipeline delete is blocked while stages exist.
- `moveToStage` refuses a converted lead and a stage from another organization; the guarded update does not overwrite a concurrent conversion.
- Summary aggregation returns zero for empty stages and matches a manual count.
- FK `ON DELETE NO ACTION` on `Lead.pipelineStageId`: a stage that holds a lead cannot be deleted, yet deleting the organization cascades cleanly.
