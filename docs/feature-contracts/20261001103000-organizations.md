# Feature Contract: Organizations & Membership

> **Status:** AGREED v1, implemented 2026-10-01. Written 2026-10-01. Builds on `20261001073651-authentication-authorization.md` (FC-AUTH-001); nothing in that contract changes.

## Decisions for v1

| # | Decision | Consequence |
|---|---|---|
| **D5** | **Organization authorization reads the membership from the DB on every organization-scoped request.** The JWT never carries `organizationId` or an organization role. | Costs one indexed read per request. Role changes and removals take effect on the next request, not after the 15-minute access-token window. This is the opposite of D1 and is the ES-recommended server-side check. |
| **D6** | **One OWNER per organization, for the life of the organization.** The creator is the OWNER. There is no ownership transfer, no leaving, and no way to assign `OWNER`. | Simple rules: nobody can remove or demote the OWNER, and nobody can grant OWNER. Guaranteed by a partial unique index, not only by code. An organization can never be orphaned, and can never change hands in v1. |
| **D7** | **Invitations are delivered by returning the raw token once to the inviter.** No email is sent. | No email infrastructure and no placeholder sender. The inviter passes the link on. Only SHA-256(token) is stored, so the token cannot be shown again; a lost token means a new invitation. |
| **D8** | **Smaller permission set than the original proposal.** Only permissions with an endpoint exist in v1; `member:update_role` is OWNER-only. | No `organization:update` / `organization:delete` (no endpoint). An ADMIN cannot usefully change roles under a "strictly outrank" rule, so granting them the permission would be misleading. |
| **D9** | **Non-members get `404 ORGANIZATION_NOT_FOUND`, never 403.** `403 INSUFFICIENT_ORGANIZATION_PERMISSION` is returned only to members who lack the permission. | Organization IDs cannot be probed to find out which exist. |
| **D10** | **A platform `ADMIN` has no special access to organizations.** | Platform role and organization role are independent. A platform ADMIN who is not a member gets 404 like anyone else. |

Unchanged from FC-AUTH-001: JWT claims, access/refresh flow, rotation and reuse detection, `User.role` (`USER`/`ADMIN`, platform level only), the response envelope, `AppError` + error codes, Clean Architecture layering.

## 2. Business Objective

Let authenticated users create organizations, invite people into them, and manage members with organization-level roles, so that one user can hold different positions in different tenants.

## 3. User Story

As an authenticated user, I want to create an organization and invite others into it, and to belong to several organizations with a different role in each, so that I can collaborate with different teams and each team controls who can do what.

## 4. Actors

| Actor | Meaning |
|---|---|
| Authenticated user | Any caller with a valid access token (`USER` or platform `ADMIN`; same rights here, see D10). |
| Org OWNER | The creator. Exactly one per organization. |
| Org ADMIN | Can read, invite `MEMBER`s and remove `MEMBER`s. |
| Org MEMBER | Can read the organization and its member list. |
| Non-member | Authenticated, but has no membership in the organization. Treated as if it does not exist (D9). |
| Anonymous | Cannot call any endpoint in this contract. |

## 5. Entry Point

N/A. API-only; no frontend in this repo. Clients call the endpoints in section 11 with `Authorization: Bearer <accessToken>`.

N/A. No frontend.

## 7. User Flow

1. A user registers and logs in (FC-AUTH-001).
2. `POST /organizations` → the user becomes OWNER of a new organization.
3. OWNER or ADMIN calls `POST /organizations/:organizationId/invitations` with an email and role. The response contains the raw invitation `token` **once**.
4. The inviter delivers the token (or an app link containing it) to the invitee out of band.
5. The invitee registers (if needed) and logs in. The invitation does not create a user.
6. The invitee calls `POST /organization-invitations/accept` with the token. The email on their account must match the invited email. A membership is created and the invitation is marked accepted, atomically.
7. Members use `GET /organizations`, `GET /organizations/:id`, `GET /organizations/:id/members`.
8. OWNER changes a member's role (`PATCH …/members/:userId`); OWNER or ADMIN removes members within the rank rules (`DELETE …/members/:userId`).

Failure paths: unknown/used/foreign/expired token on accept; inviting someone who is already a member or already has a pending invitation; acting on an organization the caller does not belong to (404); acting beyond one's rank (403).

| Field | Type | Required | Validation |
|---|---|---|---|

| Field | Type | Required | Validation |
|---|---|---|---|
| `role` | `"ADMIN"` \| `"MEMBER"` | yes | `OWNER` is rejected as `VALIDATION_ERROR` (D6) |

**Path params:** `:organizationId` and `:userId` must be UUIDs, otherwise `VALIDATION_ERROR`.

## 9. Validation Rules

- All input is validated with Zod in the controller via `parseOrThrow` before any use case runs.
- Invitation email is lowercased and trimmed so one address maps to one invitation key.
- Unknown body fields are ignored (same as FC-AUTH-001).
- Slug generation: lowercase; strip diacritics; non-alphanumerics become `-`; collapse repeats; trim `-`; cut at 48 chars; if empty use `org`. On collision append `-` plus 4 random hex chars; retry up to 5 times, then fail with `INTERNAL_SERVER_ERROR`.

## 10. Business Rules

**Roles and permissions** (application-code mapping, in `src/domain`; no DB-configurable RBAC):

| Permission | OWNER | ADMIN | MEMBER |
|---|---|---|---|
| `organization:read` | ✅ | ✅ | ✅ |
| `member:read` | ✅ | ✅ | ✅ |
| `member:invite` | ✅ | ✅ | ❌ |
| `member:remove` | ✅ | ✅ | ❌ |
| `member:update_role` | ✅ | ❌ | ❌ |

**Rank:** `OWNER > ADMIN > MEMBER`. A permission is necessary but not sufficient; these rules also apply.

- **Invite:** OWNER may invite `ADMIN` or `MEMBER`; ADMIN may invite `MEMBER` only (otherwise `INSUFFICIENT_ORGANIZATION_PERMISSION`). `OWNER` can never be invited.
- **Remove:** the target must be a member (`MEMBERSHIP_NOT_FOUND`). The OWNER can never be removed, including by themselves (`CANNOT_REMOVE_OWNER`). The actor must strictly outrank the target: OWNER removes ADMIN/MEMBER; ADMIN removes MEMBER only (otherwise `INSUFFICIENT_ORGANIZATION_PERMISSION`). There is no leaving in v1: ADMIN/MEMBER removing themselves fails through these same rules.
- **Role change:** OWNER only. The target must be a member (`MEMBERSHIP_NOT_FOUND`) and must not be the OWNER (`CANNOT_CHANGE_OWNER_ROLE`). Allowed results are `ADMIN` or `MEMBER`. Setting the role a member already has is a successful no-op.
- **Single owner (D6):** enforced by a partial unique index on `(organizationId) WHERE role = 'OWNER'`, in addition to the code rules.
- **One membership per user per organization** (unique `(organizationId, userId)`).
- **Invitations:** expire 7 days after creation. Token is 32 random bytes, base64url. Only SHA-256(token) is stored. One *open* invitation per `(organizationId, email)`: a second invite while one is open fails with `INVITATION_ALREADY_EXISTS`; once the earlier one has expired, inviting again replaces it. Inviting an email that already belongs to a member of the organization fails with `MEMBERSHIP_ALREADY_EXISTS`.
- **Accept:** the caller's account email (read from the DB, since it is not in the JWT) must equal the invited email. Order of checks: unknown/accepted token or email mismatch → `INVALID_INVITATION` (one code, so a token holder who is not the invitee learns nothing); then expiry → `INVITATION_EXPIRED`; then existing membership → `MEMBERSHIP_ALREADY_EXISTS`.
- **Tenant isolation:** `organizationId` in the path is untrusted. Every organization-scoped endpoint first resolves the caller's membership for that organization (D5, D9); no membership → `ORGANIZATION_NOT_FOUND`.
- Invitations never create users.

## 11. API Contracts

All routes are under `/api/v1`, all require `Authorization: Bearer <accessToken>`, and all use the standard envelope `{ success, message, data, error, meta: { timestamp } }`. Every endpoint can additionally fail with `UNAUTHORIZED`, `INVALID_ACCESS_TOKEN` or `ACCESS_TOKEN_EXPIRED` (401) from `authenticate`.

### 11.1 `POST /api/v1/organizations`
- **Body:** `{ "name" }`
- **201:** message `Organization created successfully.`
```json
"data": { "organization": { "id": "uuid", "name": "Acme Technologies", "slug": "acme-technologies", "role": "OWNER" } }
```
- **Failures:** 400 `VALIDATION_ERROR`

### 11.2 `GET /api/v1/organizations`
- Lists the caller's organizations, oldest membership first. No pagination in v1.
- **200:** message `Organizations retrieved successfully.`
```json
"data": { "organizations": [ { "id": "uuid", "name": "...", "slug": "...", "role": "OWNER" } ] }
```

### 11.3 `GET /api/v1/organizations/:organizationId`
- **Permission:** `organization:read`
- **200:** message `Organization retrieved successfully.`
```json
"data": { "organization": { "id": "uuid", "name": "...", "slug": "...", "role": "MEMBER", "createdAt": "ISO-8601" } }
```
- `role` is the caller's role in that organization.
- **Failures:** 400 `VALIDATION_ERROR` (bad UUID), 404 `ORGANIZATION_NOT_FOUND`

### 11.4 `POST /api/v1/organizations/:organizationId/invitations`
- **Permission:** `member:invite` (plus the invite rules in section 10)
- **Body:** `{ "email", "role"? }`
- **201:** message `Invitation created successfully.`
```json
"data": { "invitation": { "id": "uuid", "email": "...", "role": "MEMBER", "expiresAt": "ISO-8601" }, "token": "<raw token, shown once>" }
```
- **Failures:** 400 `VALIDATION_ERROR`, 404 `ORGANIZATION_NOT_FOUND`, 403 `INSUFFICIENT_ORGANIZATION_PERMISSION`, 409 `MEMBERSHIP_ALREADY_EXISTS`, 409 `INVITATION_ALREADY_EXISTS`

### 11.5 `GET /api/v1/organizations/:organizationId/members`
- **Permission:** `member:read`. Ordered by join date ascending. No pagination in v1.
- **200:** message `Members retrieved successfully.`
```json
"data": { "members": [ { "userId": "uuid", "name": "...", "email": "...", "role": "OWNER", "joinedAt": "ISO-8601" } ] }
```
- **Failures:** 400 `VALIDATION_ERROR`, 404 `ORGANIZATION_NOT_FOUND`

### 11.6 `PATCH /api/v1/organizations/:organizationId/members/:userId`
- **Permission:** `member:update_role`
- **Body:** `{ "role": "ADMIN" | "MEMBER" }`
- **200:** message `Member role updated successfully.`
```json
"data": { "member": { "userId": "uuid", "role": "ADMIN" } }
```
- **Failures:** 400 `VALIDATION_ERROR`, 404 `ORGANIZATION_NOT_FOUND`, 403 `INSUFFICIENT_ORGANIZATION_PERMISSION`, 404 `MEMBERSHIP_NOT_FOUND`, 403 `CANNOT_CHANGE_OWNER_ROLE`

### 11.7 `DELETE /api/v1/organizations/:organizationId/members/:userId`
- **Permission:** `member:remove` (plus the remove rules in section 10)
- **200:** message `Member removed successfully.`, `"data": null`
- **Failures:** 400 `VALIDATION_ERROR`, 404 `ORGANIZATION_NOT_FOUND`, 403 `INSUFFICIENT_ORGANIZATION_PERMISSION`, 404 `MEMBERSHIP_NOT_FOUND`, 403 `CANNOT_REMOVE_OWNER`

### 11.8 `POST /api/v1/organization-invitations/accept`
- **Auth:** access token only; no organization context (the caller is not a member yet).
- **Body:** `{ "token" }`
- **200:** message `Invitation accepted successfully.`
```json
"data": { "organization": { "id": "uuid", "name": "...", "slug": "..." }, "role": "MEMBER" }
```
- **Failures:** 400 `VALIDATION_ERROR`, 400 `INVALID_INVITATION`, 410 `INVITATION_EXPIRED`, 409 `MEMBERSHIP_ALREADY_EXISTS`

## 12. Backend Processing Flow

### 12.1 Layering

Same rules as FC-AUTH-001: `src/domain` and `src/application` import no `express`, `@prisma/*`, `jsonwebtoken`, `bcrypt` or `pg`. Use cases depend only on interfaces. One class per operation.

### 12.2 Folder structure (additions)

```
src/infrastructure/http/controllers/OrganizationController.ts
src/app/middleware/organization.middleware.ts   requireOrganizationMembership(), requireOrganizationPermission()
```

### 12.3 Repository interfaces (only what the use cases call)

- `OrganizationRepository`: `createWithOwner(data, ownerUserId): Promise<Organization | null>` (one transaction: organization + OWNER membership; returns `null` if the slug is taken), `findById`, `findBySlug` (used for slug collision checks), `listByUserId`.
- `OrganizationMembershipRepository`: `findByOrganizationAndUser`, `listByOrganization` (with user name/email), `updateRole(orgId, userId, role): Promise<boolean>` (guarded `WHERE role <> 'OWNER'`; `false` if no row matched), `remove(orgId, userId): Promise<boolean>` (same guard).
- `OrganizationInvitationRepository`: `create(data)` (one transaction: delete expired unaccepted invitations for this `(org, email)`, then insert; unique violation → `INVITATION_ALREADY_EXISTS`), `findByTokenHash`, `accept(invitation, userId, now): Promise<boolean>` (one transaction: `updateMany WHERE id AND acceptedAt IS NULL AND expiresAt > now`; `false` if 0 rows; then create membership; a unique violation rolls everything back and surfaces as `MEMBERSHIP_ALREADY_EXISTS`).

`TokenService.hashToken` is reused for the invitation token hash. Random token generation sits behind a small injectable function so unit tests are deterministic.

### 12.4 Per-operation flow

**Organization-scoped routes:** `authenticate` → `requireOrganizationMembership` (validate UUID → `findByOrganizationAndUser(orgId, req.user.id)` → none → `ORGANIZATION_NOT_FOUND`; else attach `{ organizationId, role }` to the request) → `requireOrganizationPermission(permission)` (role lacks it → `INSUFFICIENT_ORGANIZATION_PERMISSION`) → controller (Zod) → use case.

- **CreateOrganization:** build slug → `createWithOwner` (retry with suffix on `null`) → return organization with `role: OWNER`.
- **InviteOrganizationMember:** check invite rule for (actor role, requested role) → find user by email; if they are already a member → `MEMBERSHIP_ALREADY_EXISTS` → generate token, hash it → `create` → return invitation + raw token. The raw token is never logged or stored.
- **AcceptOrganizationInvitation:** hash token → `findByTokenHash` → missing/accepted → `INVALID_INVITATION` → read caller from `UserRepository`, email mismatch → `INVALID_INVITATION` → expired → `INVITATION_EXPIRED` → `accept(...)`; `false` means a concurrent accept or expiry won → `INVALID_INVITATION`.
- **ListOrganizationMembers / GetOrganization / ListUserOrganizations:** read and map to DTOs.
- **UpdateOrganizationMemberRole:** find target → `MEMBERSHIP_NOT_FOUND` / `CANNOT_CHANGE_OWNER_ROLE` → no-op if equal → `updateRole`; `false` → `CANNOT_CHANGE_OWNER_ROLE`.
- **RemoveOrganizationMember:** find target → `MEMBERSHIP_NOT_FOUND` → target OWNER → `CANNOT_REMOVE_OWNER` → actor must outrank target → `remove`; `false` → `CANNOT_REMOVE_OWNER`.

Wiring only in `src/app/container.ts` (and `server.ts` for the real implementations). `buildContainer` gains the three repositories as parameters.

## 13. Database Impact

New tables (new migration; the `init_auth` migration is never edited):

```prisma
enum OrganizationRole { OWNER ADMIN MEMBER }

model Organization {
  id          String   @id @default(uuid())
  name        String
  slug        String   @unique
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
  memberships OrganizationMembership[]
  invitations OrganizationInvitation[]
}

model OrganizationMembership {
  id             String           @id @default(uuid())
  organizationId String
  userId         String
  role           OrganizationRole
  createdAt      DateTime         @default(now())
  updatedAt      DateTime         @updatedAt
  organization   Organization     @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  user           User             @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([organizationId, userId])
  @@index([userId])
}

model OrganizationInvitation {
  id             String           @id @default(uuid())
  organizationId String
  email          String
  role           OrganizationRole
  tokenHash      String           @unique
  expiresAt      DateTime
  acceptedAt     DateTime?
  invitedBy      String
  createdAt      DateTime         @default(now())
  organization   Organization     @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  inviter        User             @relation(fields: [invitedBy], references: [id], onDelete: Cascade)

  @@index([organizationId])
  @@index([email])
}
```

Compared with the original proposal: no standalone `@@index([organizationId])` on memberships (the unique index already leads with it), no `revokedAt` (no revoke endpoint in v1), `invitedBy` is a real foreign key, and `@@index([expiresAt])` is dropped (no purge job in v1).

**Hand-written SQL in the migration** (Prisma cannot express partial indexes; review the SQL before committing):

- `CREATE UNIQUE INDEX ... ON "OrganizationMembership" ("organizationId") WHERE "role" = 'OWNER';` (D6)
- `CREATE UNIQUE INDEX ... ON "OrganizationInvitation" ("organizationId", "email") WHERE "acceptedAt" IS NULL;` (one open invitation per email; expired rows are deleted by `create` inside its transaction before inserting)

**Transaction boundaries:** `createWithOwner`, `accept`, and invitation `create` are each a single transaction. `updateRole` and `remove` are single guarded statements.

## 15. Error Codes

New codes (each must be added to `ERROR_HTTP_STATUS`, `ERROR_DEFAULT_MESSAGE`, the docs and this contract):

| Code | HTTP | When |
|---|---|---|
| `ORGANIZATION_NOT_FOUND` | 404 | Organization does not exist **or the caller is not a member** (D9) |
| `INSUFFICIENT_ORGANIZATION_PERMISSION` | 403 | Member lacks the permission, or does not outrank the target / requested role |
| `MEMBERSHIP_NOT_FOUND` | 404 | Target user is not a member of the organization |
| `MEMBERSHIP_ALREADY_EXISTS` | 409 | Inviting or accepting for a user who is already a member |
| `CANNOT_REMOVE_OWNER` | 403 | Attempt to remove the OWNER (including self-removal by the OWNER) |
| `CANNOT_CHANGE_OWNER_ROLE` | 403 | Attempt to change the OWNER's role |
| `INVITATION_ALREADY_EXISTS` | 409 | An open (unaccepted, unexpired) invitation exists for that email |
| `INVITATION_EXPIRED` | 410 | Valid token for the right user, but past `expiresAt`; ask for a new invitation |
| `INVALID_INVITATION` | 400 | Unknown token, already accepted, or the caller's email does not match |

Reused: `VALIDATION_ERROR`, `UNAUTHORIZED`, `INVALID_ACCESS_TOKEN`, `ACCESS_TOKEN_EXPIRED`, `ROUTE_NOT_FOUND`, `INTERNAL_SERVER_ERROR`.

Dropped from the original proposal: `ORGANIZATION_ACCESS_DENIED` (replaced by 404, D9), `INVITATION_NOT_FOUND`, `INVITATION_ALREADY_ACCEPTED` and `INVITATION_REVOKED` (folded into `INVALID_INVITATION`, or not applicable without a revoke endpoint). `ERROR_HTTP_STATUS` needs a 410 mapping, which is new.

## 20. Test Cases

**Unit** (in-memory fakes; new fakes are additive in `tests/helpers/fakes.ts`)

- Permission map: every role/permission pair in the section 10 table; rank rules for invite, remove and role change.
- CreateOrganization: creates OWNER membership; slug rules (diacritics, symbols, empty → `org`, 48-char cut); collision retries with a suffix; gives up after 5.
- InviteOrganizationMember: ADMIN cannot invite ADMIN; `MEMBERSHIP_ALREADY_EXISTS`; `INVITATION_ALREADY_EXISTS`; only the hash is stored, and the raw token differs from it.
- AcceptOrganizationInvitation: success; unknown token, accepted token and email mismatch all give `INVALID_INVITATION`; expired gives `INVITATION_EXPIRED`; already a member gives `MEMBERSHIP_ALREADY_EXISTS`.
- UpdateOrganizationMemberRole: OWNER-only; `CANNOT_CHANGE_OWNER_ROLE`; `MEMBERSHIP_NOT_FOUND`; same-role no-op.
- RemoveOrganizationMember: OWNER removes ADMIN and MEMBER; ADMIN removes MEMBER but not ADMIN or OWNER; `CANNOT_REMOVE_OWNER` including self; MEMBER denied; ADMIN removing self denied.

**Integration, HTTP** (real app + `_test` database)

- Full lifecycle: register two users → create org → invite → accept → list members → change role → remove.
- Tenant isolation: a user in org A calling any `/organizations/:B/...` endpoint gets 404 `ORGANIZATION_NOT_FOUND`; the response is identical to that for a non-existent org id. A platform ADMIN who is not a member also gets 404.
- Role change and removal take effect on the very next request, using the same still-valid access token (D5).
- Token in the invite response is not stored: the DB row has only `tokenHash`, and `SHA-256(token) == tokenHash`.
- Accept with a different user's account → `INVALID_INVITATION`; accept twice → second is `INVALID_INVITATION`.
- Envelope, status code and `error.code` for every failure in section 15; bad UUID → `VALIDATION_ERROR`; `role: "OWNER"` → `VALIDATION_ERROR`.
- Missing or invalid access token on each endpoint → 401.

**Integration, repositories** (real SQL; each protection must be proven by a test that fails when the protection is removed, as in `repositories.test.ts`)

- `createWithOwner` is atomic: if the membership insert fails, no organization row remains. Duplicate slug returns `null`.
- Partial unique index: inserting a second OWNER for the same organization fails at the DB.
- `accept` guard: a second concurrent accept (run two in parallel) yields exactly one membership and one `true`; an expired invitation yields `false` and no membership; a membership unique violation rolls back the `acceptedAt` update.
- Invitation `create`: duplicate open invitation fails; an expired one is replaced.
- `updateRole` and `remove` never affect an OWNER row (return `false`).
